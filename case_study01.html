Programming Decay

Problem

Urban designers do not lack drawing tools. They lack a reusable, explainable decision chain between site data, strategy selection, spatial generation, and post-occupancy monitoring.

城市更新设计师真正缺的不是出图工具,而是一个能把"数据证据 — 策略选择 — 空间生成 — 后期监测"串起来的可复用决策链。

让设计师从"画策略"变成"选策略"——把出图工具变成决策伙伴。

This case study documents how I reframed a thesis system into an AI product hypothesis. Current status: research prototype / concept validation stage. 本 case study 记录我如何把毕设系统重构成一个 AI 产品假说;当前状态:研究原型 / 概念验证阶段,尚无真实付费用户。

面向城市更新规划师和景观设计师, 打通"多源数据证据 → 场地特定的策略组合 → ML 空间生成 → 持续监测反馈"的决策链路。

每一个空间方案都能反向追溯到具体的 GIS 特征值。

Why I reframed it

做毕设时我反复推翻早期判断 ——"数据从哪来 / 策略选哪几个 / 选完怎么落地"这些前期决策每次都从零开始, 没有可以复用的工具。加上之前在上海设计事务所实习时观察到的共性: 资深设计师做这些决策靠经验、缺量化辩护, 常成为投标失败的原因。

这让我把项目换了一个视角: 传统设计 brief 把决策链路当黑箱, AI 工具应该把它当 first-class citizen —— 每一步都可复用、可追溯、可优化。

所以这不是更快的出图工具 —— 是把决策链路从黑箱打开。

市场定位 — 为什么是这个空白象限

  • AIGC tools — strong visual generation, weak evidence traceability Midjourney · 即梦 · Maket · LookX
  • GIS tools — strong data analysis, weak design generation ArcGIS Insights · Esri Site Suitability
  • Programming Decay — connects evidence, strategy, generation, and monitoring

把现有 AI / 设计工具按两个维度切: 横轴是「创意生成 ←→ 决策分析」, 纵轴是「单点工具 ←→ 完整链路」。

格局清晰: 左下半区被 Midjourney / 即梦 / Maket / LookX 占满 (创意生成 + 单点工具); 右下角是 ArcGIS / Esri Site Suitability 这种传统 GIS 决策工具 (数据分析, 但只做选址或图层叠加)。右上角"数据 + 完整链路"基本空白 —— 这正是 Programming Decay 的产品定位。

这不是巧合。"完整链路"是工程上昂贵的承诺: 垂直 AIGC 公司不擅长后端数据链路, 传统 GIS 公司不会 ML 生成。能站在右上角的产品, 必须从第一天就按"决策伙伴"而不是"出图工具"来设计。

用户旅程 — 谁用、怎么用

USER · INTERACTION

Programming Decay 服务两类核心用户: 城市更新规划师 (P1, 做前期方案决策) 和 景观设计师 (P2, 做棕地 / 工业遗址改造)。两者共享前半段决策链路 (数据 → 选址 → 三角验证), 在后半段 (策略偏好 / 输出格式 / 监测重点) 按场景分叉。

P1 的工作流以"投标依据"为锚点 —— 他们要的是可解释的策略组合 + 监测反馈 (项目交付后能持续证明方案有效, 是甲方再委托的基础)。P2 的工作流以"生态修复深度"为锚点 —— 他们要的是生态指标量化报告 + Rhino 兼容输出 + 长期生态跟踪。

同一产品, 同一条决策链路, 但 P1 看到的是"投标资产", P2 看到的是"生态修复工具" —— persona-aware 不是为每个用户造一个产品, 而是同一产品在不同阶段提供不同 affordance。

How it works — 4 步产品体验

PRD v0.2 完整 6 段链路在 v3.1 demo 里展开。Case Study 这里讲产品级别的 4 步用户体验:

  1. 1. Sense INPUT

    用户上传场地 + 项目目标; 系统从多源开放数据抓取 GIS 图层加权; 输出风险底图 + 优先区清单。

  2. 2. Classify SYSTEM LOGIC

    用户可调网格切分; K-Means 聚类 + Entropy Atlas 居民情感双路径验证; 输出 cell 清单 + 三角证据。

  3. 3. Generate SYSTEM LOGIC

    基于 cell 特征做策略推导 + Pix2Pix / NCA 流水线; 输出场地特定的策略组合 + 矢量空间方案。

  4. 4. Deploy OUTPUT

    ML 输出转化为场地特定的部署系统 (每个场地的具体部署形态由场地特征决定); 输出可部署空间产品 + 监测仪表盘 + 数据回流闭环。

v0.2 实现状态: Sense + Classify 已跑通 (Dagenham Dock, 6 英国数据源 + 8×8 默认网格); Generate Pix2Pix 跑通 12 epoch / NCA 流水线尚未打通; Deploy 概念已定 / Dagenham Dock 部署形态 (4 塔 + 4 nodes) 仍迭代。

AI Decision Chain — 哪一步用什么级别的 AI

不是"什么都扔给最贵的模型"。Programming Decay 各步骤的 AI 边界:

步骤 v0.2 主导技术 LLM 加成可能位置
SenseRule-Based API 抓取用户对话式 refine (尚未实现)
Classify经典 ML (K-Means 客观聚类)—
Generate经典深度学习 (Pix2Pix + NCA)策略推导文字解释 (尚未实现)
DeployRule-Based 监测规则—

I deliberately kept LLMs out of the core decision engine in v0.2, because the highest-risk task here is not language generation, but explainable spatial decision-making. v0.2 我刻意把 LLM 排除在核心决策引擎之外 —— 这里最高风险的任务不是语言生成, 而是可解释的空间决策。

v0.2 以经典 CV / ML 为主, LLM 加成 (对话层 / 策略解释层) 尚未实现。这一边界对应 PRD 1.3: 这不是"通用 AI 出图", 是"针对场地决策链路的可解释 AI"。

Product Lens

这个项目可以读作一个面向场地决策链路的可解释 AI 产品——不是出图工具, 是决策伙伴。

核心用户是城市更新规划师与景观设计师 (P1 / P2), 他们需要在前期方案阶段做"数据从哪来 / 策略选哪几个 / 选完怎么落地"三个决策, 并且需要可量化辩护以应对投标场景。

我把工作组织成三轴: 数据 / 输入 (多源 GIS + 社区情感双路径)、系统逻辑 (K-Means 客观聚类 + Entropy Atlas 三角验证 + Pix2Pix / NCA 流水线)、交互 (persona-aware, 同一产品在不同阶段输出不同 affordance)。

MVP 聚焦在 Sense + Classify 已跑通的链路 + 5-8 位真实用户测试, 先验证"决策伙伴"定位是否成立。

主要产品风险是规划师不愿意改变工作流——资深合伙人拍板 vs 算法选址 + 白盒可解释, 是工作流层面的改动而非工具层面的加速。验证方法: 找 5-8 位真实规划师 / 景观师做产品测试, 看至少 3 位能否反馈"愿意继续使用 / 推荐给同事"。

下一步 ship 的是 v0.5 (2026.10): 完整 Pix2Pix → NCA 流水线打通 + Hub 设计冻结一个参考实现 + 至少 3 个真实场地跑出过完整流程。

Decisions & Trade-offs

决策 1 — 决策伙伴 vs AI 出图工具

AIGC 出图工具是红海, 决策链路这一层无人接管。Programming Decay 选的是后者。

PRD v0.1 写完后通读毕设, 发现框架放在"出图速度"上, 但毕设的真实价值是"证据 → 策略 → 生成 → 部署"四步链路 —— 这两条不属于同一种产品, 整体重写 v0.2。

重写时桌面上 3 条路径:

  • A · ToG 棕地修复 SaaS, 最贴近真实毕设但销售周期长、和 PM 求职主线偏离
  • B · 决策伙伴 (城市更新规划师 / 景观设计师), 保留所有真实技术内核, 用户仍是设计师
  • C · 双线并行, 工作量过大

选 B。验证: 5-8 位真实规划师 / 景观师线上访谈, 看"决策伙伴"这个词他们能否翻译出对应工作流环节。翻译不出来定位就不成立。

决策 2 — PRD v0.1 推翻整体重写, 不打补丁

发现框架错了之后, 真正贵的不是重写, 是不重写。

打补丁推不下去:"出图速度"和"决策链路"是两套维度, 硬塞同一份文档, 下游所有内容 (Architecture / Case Study / 微交互 spec) 都会在两套语言之间持续换算, 成本沿决策树指数累积。

接受沉没成本, 整体重写 v0.2。

决策 3 — 熵图集嵌入 v3.1 demo Selection 环节, 不放主站首页

对"算法黑箱"的质疑, 答案不是在叙事里多解释, 是给第二条独立证据链。

K-Means 在 v3.1 demo 里给出客观选址。但"算法凭什么排这一块"是任何决策类 AI 产品都要预答的标准质疑。Programming Decay 的回答是熵图集 —— 在 Dagenham Dock 这个 case 里, 137 条本地评论 / 67 个地点 / 44% 标记 Decay & Neglect 的社区情感数据走的是完全不同的方法路径, 两条路径在同一片区域收敛。

候选位置 3 个: A 嵌入 case study 当一段静态叙事; B 保持主站首页"03 技术实验"独立卡片; C 拆码合并到 v3.1 主 JS。最终用 iframe 嵌入到 v3.1 Selection 环节、K-Means priority queue 之后, 保留独立交互。理由是三角验证需要"实时打开两张地图对比"的体感: 静态叙事承载不了, 独立卡片失去逻辑关联, 拆码破坏现有结构。

决策 4 — 模型置信度低时主动降级, 不强行输出策略

AI 输出边界拉不清, 设计师就会被"看起来像"的方案误导。

Generate 步骤依赖 Pix2Pix / NCA 等模型。数据信号弱 / case 偏离训练分布 / cell 特征极端时, 模型输出会不稳。

设计选择: 检测到 low confidence, 主动降级 —— 把"自动生成策略组合"切换为"显示该 cell 的 GIS 信号 + 邻近 cell 的策略参考 + 用户手动 override"。

考虑过的两条路:

  • A · 模型在所有情况下都强行输出 (用户体验"流畅"但产品边界不清)
  • B · 常驻 confidence 标签让用户自己判断 (信息密度高但责任推给用户)

选主动降级 + bad case 提示。

已知风险 — 我打算怎么验证 / 怎么 fallback

3 条 disconfirming evidence 我已经知道, 不藏:

规划师可能不愿意改变工作流。 Programming Decay 把"凭经验 + 资深合伙人拍板"换成"算法选址 + 白盒可解释", 这是工作流层面的改动, 不是工具层面的加速。如果 v0.5 用户测试出现"工具好但我们就是不会用"的反馈, 当前定位需要重做 —— 可能切到"决策辅助"而不是"决策伙伴", 让规划师保留拍板权, 工具只输出证据链。

大型设计院倾向自建 AI 工具。 院内自建路径优势是数据合规 + 内部数据闭环, 我的护城河靠"四策略 OS + Hub 监测反馈"两块研究投入大、复制成本高的部分。如果 v0.5 出现院内自建竞品, 商业化路线必须从"卖给大院"切到"卖给中小事务所 + 政府委托设计单位"。

NCA 损失函数可能不收敛。 Pix2Pix → NCA 流水线是 v0.5 工程主路径, 但 NCA 的损失函数 (面积比例 + 空间连续性) 可能训练不收敛。fallback: 降级用基于规则的策略分区系统, 牺牲生成新颖度换可控性。
