# MemoryOS v0.3.1 PRD — Memory Inbox 为核心，MCP / 浏览器插件为入口
版本：v0.3.1 · 日期：2026-06-02 · 作者：Jiajia
方向 B（结构化项目工作记忆 / 多 AI 知识工作者）

架构（v0.3 起）：核心 = Memory Inbox + Review 入库（通道无关）；MCP / 浏览器插件只是写进 Inbox 的入口。三层：P0 核心层 Inbox / P0 通道 A 本地 MCP（先打通 1 个客户端）/ P1 通道 B 浏览器插件（验证后再做）。
v0.3.1 实现对齐补丁（已合并进正文，逐条对应章节，给多 agent 协作消歧）：
  1. 来源字段拆分（§4.2）：sourceChannel（manual/mcp/browser）+ sourceClient（Claude Desktop/Codex/ChatGPT Web…）；sourcePlatform 设为可选/可空（常不可靠）。cross_ai_reuse 以 sourceClient 为准。
  2. 埋点改通道无关（§4.2）：事件带 channel 字段；按"写入进程"分文件避免并发写竞争——app 写 telemetry.jsonl，server 写 telemetry.server.jsonl，不再用 mcp. 前缀。
  3. Inbox handoff schema 对齐现有 ParsedHandoff 字段名（§4.2/§5.1），新增三个转换函数 parsedToInboxHandoff / inboxHandoffToMarkdown / inboxItemToReviewState。
  4. 导入即 Review（§4.3/§6）：手动粘贴导入后"写 Inbox 并立即打开该 item 的 Review"；定义「取消=保留 pending」「丢弃=移 archive(discarded)」。
  5. session 文件名防覆盖（§7）：同分钟 apply 两条会覆盖；冲突时自动加 _2/_3（或加秒/uuid）。
  6. server 写 Inbox 要原子写 + 路径 containment（§7）：tmp → rename；校验解析后真实路径仍在 workspace 内，拒 ../symlink 逃逸。
小修：Phase 0 措辞（sourceTool 必接通；aboutMe 从结束指令移除）；矩阵 "Kimi Code CLI" 配置路径 ~/.kimi/mcp.json；P1 插件补 Native Messaging host manifest + allowed_origins。

0.给 co-work 的执行说明

角色：在现有 v0.1.2 代码（Tauri + React + TS）上，先把"待审记忆 Inbox + Review 入库"做成通道无关的核心，再接第一个 MCP 客户端。浏览器插件本期不写代码，只在 PRD 里定义。

Red lines：

  1. 不自动静默抓取：任何通道写回的 handoff 一律先进 Inbox，必须用户 review 后才入库。
  2. 运行期不传输用户数据：server 运行时不开监听端口、不联网上传任何用户内容；埋点纯本地。（注：安装/更新软件本身可能访问分发渠道如 npm，不涉及用户数据外泄。优先把 server 随 app/.mcpb 打包。）
  3. 不做账号 / 云同步 / 后端 / 多账户。

执行方式：按 §9 Phase 顺序，每 Phase 跑 §8 自测再下一个。复用现有纯逻辑（§4.2）；文件读写在 server 端用 Node fs 按同一契约重写。

0.5技术现实硬约束

  1. 本地 MCP server 只能被本地客户端连接（stdio / 本地配置）：Claude Desktop、Claude Code、Codex（CLI+IDE 扩展）、Cursor / Windsurf / VS Code / Cline、Kimi Code CLI。
  2. ChatGPT / Kimi 聊天 app / DeepSeek / Gemini 的网页·桌面聊天端连不上本地 server。技术上有 remote MCP / 隧道，但引入联网/账号/权限复杂度——本期 P0 主动不采用。这些走 Inbox 的"复制粘贴/插件"入口。
  3. .mcpb 是开放规范（已并入 MCP 项目）；当前优先服务 Claude Desktop / Claude Code / MCP for Windows，其他本地客户端用 JSON/TOML 配置兜底，指向同一 server。
  4. prompts 原语 GUI 支持不均；tools 为骨架，prompts 可选。
  5. fs.ts 依赖 Tauri，不能给 Node server 直接用；可共享纯逻辑：parseHandoff / parseSessionFile / extractSuperseded / editPercent / prompt builder。
  6. 埋点在 %APPDATA%/memoryos/，不在 workspace。
  7. 模型不保证每次调 save_session_handoff；指令显式要求 + 保留复制粘贴导入兜底。

1.需求

1.1 痛点

多 AI 协作做一个项目时切换 AI，丢失结构化项目状态（决策、文件位置、handoff、待办、踩坑）；现状靠手动复制粘贴。

1.2 目标用户

跨多个 AI 做真实项目的知识工作者；同时有多个项目；一部分用本地 agent（Codex/Cursor/Claude Desktop），一部分只用网页聊天 AI——这正是为什么要"通道无关 Inbox"。

1.3 差异化（P0，已据 Codex 修正）

竞品两类：静默抓取+自动注入型（OpenMemory/Rethread）；human-in-the-loop 可携带文件型（Memory Sync：Memory.md + Pull/Edit/Push + 用户审核，理念接近 MemoryOS）。

MemoryOS 独有点（差异化锁定这两条，刻意不堆亮点）：

  1. 按项目分库的多项目结构（per-project context/decisions/handoff/sessions，竞品多是一份关于"你"的 user-level memory）。
  2. 结构化决策演进（decisions.md + supersede 划线合并，记录决策如何被推翻/迭代）。
切分：竞品 = user-level portable memory；MemoryOS = project-level structured handoff + review + supersede。目标是把核心问题解决干净 + 清晰差异化叙事，不建"赢家通吃"壁垒。

1.4 优先级 / 非目标

  • P0：Inbox + Review 入库；打通一个本地 MCP 客户端（通道 A）。
  • P1：浏览器插件通道（通道 B），做之前先验证用户是否真在网页聊天里。
  • 非目标：静默全自动抓取入库；账号/云/后端/多账户；为覆盖网页端做公网暴露/隧道；为差异化再堆亮点。

2.产品规划（三层）

P0 核心层 — Memory Inbox + Review 入库（通道无关）
   ├─ P0 通道 A — 本地 MCP（先打通 1 个客户端）
   └─ P1 通道 B — 浏览器插件（Chrome-only，验证后再做）
所有通道只做一件事：把一份 handoff 送进 Inbox。入库永远在桌面 app review。
  • 0-1：核心层 + 通道 A（一个客户端）跑通；网页聊天 AI 暂走复制粘贴入口。
  • 1-2：若验证显示用户多在网页聊天，做通道 B；记忆质量、跨项目搜索、MCP resources。
  • 长期：按目标 AI 自动调 prompt；团队共享（重评红线）。

3.业务架构（功能模块 M0–M8）

模块阶段说明
M0 Memory Inbox（核心）0-1.memoryos/inbox/ 存待审结构化 handoff；badge 计 status=pending；review/apply/discard；apply/discard 后移 .memoryos/archive/。所有通道写这里。
M1 本地 MCP server（通道 A）0-1Node.js 本地 stdio server，tools 为骨架 + 可选 prompts；save_session_handoff 写 Inbox。
M2 Review 入库0-1复用现有 UpdateSuggestion + supersede 划线 + ReviewPage；apply 写 session + 合并 context/decisions。
M3 server 打包分发0-1优先随 app/.mcpb 打包。产出 Claude Desktop .mcpb。
M4 复制粘贴入口0-1现有复制指令 + ImportHandoffModal（parseHandoff→结构化→写 Inbox→立即 Review）。
M5 连接状态 + 待审通知0-1连接状态 + Inbox pending badge。
M6 连接教程页0-1开始教程页按客户端给指引（§5.5）。
M7 浏览器插件（通道 B）1-2Chrome-only，覆盖 ChatGPT + Claude web；user-click + review，不静默。先验证再做。
M8 多账户/团队1-2占位。

4.实现架构

4.1 逻辑层

  • Pull（通道 A）：客户端触发 → get_project_memory(project) → server 读 about_me.md + 项目 00_context.md/decisions.md + 最新 session Compact Context → 组装返回 → AI 回述一句话理解后继续。
  • Push（写 Inbox，所有通道统一为结构化 handoff）：MCP 模型调 save_session_handoff 传结构化字段 → server 直接构造 Inbox item；复制粘贴走 parseHandoff → parsedToInboxHandoff → 写 Inbox → 立即打开 Review。Inbox 里永远是同一结构（= ParsedHandoff），review 不区分来源。
  • 算法（纯逻辑共享）：parseHandoff（仅复制粘贴路径）、Compact 抽取、extractSuperseded；项目名简单匹配，不上向量。

4.2 数据层

workspace/
  about_me.md
  projects/<slug>/ { project.json, 00_context.md, decisions.md, sessions/session_YYYY-MM-DD_HHmm[_n].md }
  .memoryos/
    inbox/   <safe-ts>_<uuid>.json     # 待审结构化 handoff（文件名 filename-safe）
    archive/ <safe-ts>_<uuid>.json     # apply/discard 后移到这里
    mcp_state.json
# 埋点不在这里！在 %APPDATA%/memoryos/

Inbox item（结构化；handoff 字段名 = 现有 ParsedHandoff 类型，直接复用）：

{ "id": "<uuid>", "slug": "<slug>",
  "sourceChannel": "manual" | "mcp" | "browser",
  "sourceClient": "Claude Desktop" | "Codex" | "ChatGPT Web" | "...",
  "sourcePlatform": "Claude" | "ChatGPT" | null,   // 可选，允许空
  "createdAt": "2026-06-02T20:31:02.123Z",
  "handoff": { /* 与 ParsedHandoff 同名同构 */
    metadata, whatWeWorkedOn, keyDecisions, currentState,
    openQuestions, nextActions,
    suggestedContextUpdate, suggestedDecisionsUpdate, suggestedAboutMeUpdate,
    compactContext },
  "status": "pending" | "applied" | "discarded" }
文件名必须 filename-safe（Windows 不允许冒号）：20260602T203102_123Z_<uuid>.json。badge 只数 status=pending；apply/discard 后移 archive/（幂等）。
三个转换函数：parsedToInboxHandoff → Inbox handoff；inboxHandoffToMarkdown → 标准 9 段 Markdown；inboxItemToReviewState → 现有 ReviewPage 的 UpdateSuggestion[]。

埋点（通道无关，纯本地）：每条事件带 channel 字段。按写入进程分文件避免并发写竞争：app 写 telemetry.jsonl，server 写 telemetry.server.jsonl。KPI：pull_success_rate / push_to_inbox_rate（北极星 = 入库 ÷ 进 inbox 总数）/ cross_ai_reuse（同项目被不同 sourceClient pull 的次数）。

4.3 表现层

交互：开始教程页含 M6；出现 pending 时 badge → review。手动导入后直接打开该 item 的 Review。Review 的「取消」= 保留 pending；「丢弃」= 移 archive/（status=discarded）。复制指令按钮保留，文案补"（网页聊天 AI 用此处复制）"。UI 复用现有规范（Notion 蓝灰 #525A6B、语义化路径、全中文 UI）。

5.MCP 接口规格（通道 A）

5.1 Tools

  • list_projects — 无输入；输出 [{slug,name,currentGoal,updatedAt}]；只读。
  • get_project_memory — 输入 {project}（容错匹配）；输出 {aboutMe,context,decisions,latestCompactContext,projectName}；只读（pull）。
  • save_session_handoff — 结构化 JSON 入参，字段名对齐 ParsedHandoff。server 据此构造 Inbox item（status=pending）写入（原子写）。输出 {staged:true, message:"已暂存到 MemoryOS，请回桌面 app 确认入库（N 条待审）"}。返回文案必须明确"尚未入库"。

5.2 Prompts（可选糖）

  • start_session(project?) → 复用 buildStartSessionPrompt（注入式，无副作用）。
  • end_session(project?) → 指示模型按 9 段结构整理本轮并调用 save_session_handoff（传结构化字段，不粘贴 Markdown）。
  • 客户端不支持 prompts 时，直接对话触发工具即可。

5.5 客户端连接教程页（M6）

严禁为不支持本地 MCP 的客户端编造 MCP 配置。 矩阵（2026-06 快照，过期重核）：

客户端本地 MCP教程页给什么
Claude Desktop✅.mcpb 双击（推荐）或 claude_desktop_config.json
Claude Code✅claude mcp add / 配置
Codex（CLI+IDE）✅~/.codex/config.toml 加 [mcp_servers.memoryos]
Cursor / Windsurf / VS Code / Cline✅各自 MCP JSON（command/args）
Kimi Code CLI✅~/.kimi/mcp.json 或 kimi mcp add
ChatGPT（网页/桌面）✕ 本期不采用引导复制粘贴；通道 B 上线后改插件
Kimi 聊天 app / DeepSeek / Gemini✕引导复制粘贴
 
# Codex ~/.codex/config.toml
[mcp_servers.memoryos]
command = "node"
args = ["<server 入口路径>"]
env = { MEMORYOS_WORKSPACE = "<用户真实 workspace 路径>" }

6.关键流程

  • A 开始（pull）：客户端触发 → get_project_memory → server 组装返回 → AI 回述理解 → 继续。
  • B 结束（push→Inbox→review→入库）：MCP 调 save_session_handoff / 复制粘贴粘进 ImportHandoffModal → 都成结构化 Inbox item（pending）。手动路径导入后立即 Review；MCP 路径回 app 见 badge 进 Review。review（划线 supersede）→ apply：inboxHandoffToMarkdown 写 session + 合并 context/decisions + 移 archive。
  • C 连接：开始教程页 → 选 AI → 按 §5.5 操作 → 测试 pull。
  • D 兜底：网页聊天 AI / 模型没调 save → 复制指令 + ImportHandoffModal，殊途同归到 Inbox。

7.技术实现要点

  • server 打包：优先随 app/.mcpb 打包；workspace 路径经 MEMORYOS_WORKSPACE 传入。
  • server↔app：独立 Node 进程 + Tauri 进程，通过 workspace 文件通信（server 写 inbox，app 读 inbox），无 RPC。
  • 原子写 + 路径 containment：tmp 文件 → rename；写前把路径解析为真实绝对路径并校验仍在 workspace 内，拒 .. 穿越与 symlink 逃逸。
  • session 文件名防覆盖：冲突时自动加 _2/_3（或加秒/uuid）。
  • pending 检测：0-1 用 app focus 时扫 inbox/（纯 JS）；fs-watch 留 1-2。
  • 隐私：运行期不开端口/不联网传用户内容；埋点本地。
  • Node 依赖：官方 MCP TS SDK，避免编译型依赖。

8.验收 / 自测清单

  • M0 Inbox：write/read/apply/discard 闭环；文件名无非法字符；apply 后不重复入库；badge 只数 pending。
  • M1/M2：list_projects/get_project_memory 与 app 逐字一致；save_session_handoff 收结构化入参、只写 inbox 不改正式文件；复制粘贴与 MCP 路径结构一致；apply 用 inboxHandoffToMarkdown 写 session；review 走通 supersede。
  • 导入体验：手动导入后直接进 Review；「取消」保留 pending、「丢弃」移 archive（不静默丢）。
  • session 防覆盖：同分钟连续 apply 两条不互相覆盖。
  • 原子写/containment：无半写文件；workspace 外路径被拒。
  • M3：随 app 打包能起 server；Claude Desktop 双击 .mcpb 成功。
  • M6：直连卡片片段复制即用（路径真实）；不支持的客户端卡片无 MCP 配置、只引导复制粘贴。
  • 红线回归：运行期无监听端口、无用户内容外传（抓包确认）；无 handoff 绕过 review 入库。

9.开发顺序

  • Phase 0（前置修复）：修 CopyPromptModal 的 sourceTool（→ sourceClient）传递；aboutMe 控件从结束指令移除。
  • Phase 1：M0 Memory Inbox 核心（write/read/apply/discard + badge + 三个转换函数）+ ImportHandoffModal 改成"parseHandoff→结构化→写 Inbox→立即 Review"。
  • Phase 2：M1 MCP server 只读骨架（list_projects + get_project_memory），先在 1 个客户端跑通 pull。建议首个客户端 Claude Desktop，其次 Codex。
  • Phase 3：save_session_handoff（结构化入参，原子写）+ end_session prompt（调工具版）。
  • Phase 4：M3 打包（随 app/.mcpb）。
  • Phase 5：M6 连接教程页（§5.5 矩阵，注入真实路径）。
  • Phase 6：埋点（带 channel 字段，app/server 分文件）+ 连接状态 UI + 可选 prompts + 红线回归。
  • （P1，验证后）：M7 浏览器插件 spike（Chrome，ChatGPT+Claude web；Native Messaging host manifest + allowed_origins；user-click+review）。

v0.3.1，Inbox 为核心、通道为入口。每完成一 Phase 同步回 00_context.md/decisions.md 并走 supersede。
